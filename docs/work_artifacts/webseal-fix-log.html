WebSeal Fix Log

The review found that the tamper detection worked but the wallet block could be bypassed by the tampered page's own code, plus false alarms on real dApps. This log lists every issue, what changed, and the test that proves it. Round 2 worked through the open items from round 1 and added an automatic demo recorder, which exposed two demo bugs. What is still open is at the end.

Core unit tests8 → 10/10all pass
CLI end-to-end4 → 8/8all pass, ENS paths included
Browser end-to-end17 → 60/60all pass, none skipped
Wallet-gate bypasses14 → 03 from review, 11 found while fixing

Wallet gate bypasses

In each case, code on a tampered page got eth_sendTransaction to the wallet. The fix assumes the page's own code is the attacker, which is the Bybit situation.

#1

Overriding a built-in turned the gate off

Critical
Was
The gate called SIGNING_METHODS.includes(method) on every request, so Array.prototype.includes = () => false let signing through.
Changed
The page-world script now saves every built-in it uses before the first page script runs. Signing methods sit in a private lookup table with no prototype. The code avoids spread, for…of and array destructuring, since those all go through the array iterator, which page code can patch.
Proof
e2e: “bypass blocked: overriding Array.prototype.includes”
packages/extension/src/main.ts
#2

Page code could forge the “ok” verdict

Critical
Was
Verdicts arrived as postMessage messages keyed with sha256(token:seq), but the check used crypto.subtle.digest from the page world. Replacing it made any key match, so a forged “ok” unlocked signing, even after the real “fail” had arrived.
Changed
Replaced the protocol with a private channel. main.ts creates a detached <webseal-channel> element, and content.ts takes it out of the document in the same injection step, before any page script runs. The status is the event type, so no getter page code could patch is involved. A handshake is accepted only while the page has no scripts yet. “fail” is sticky until reload.
Proof
e2e: “overriding crypto.subtle.digest and posting a forged verdict”, “forged status message from the page does not unblock”
main.ts · content.ts · new channel.ts
#3

Same-origin iframes and popups had an unguarded wallet

Critical
Was
WebSeal only ran in the top frame. A tampered page could create a same-origin iframe and use iframe.contentWindow.ethereum directly.
Changed
Both scripts now run in all frames, including about:blank, srcdoc and blob: ones. A same-origin subframe, or a window opened by a same-origin page, takes the worse of its own verdict and the related page's. A failure in either one fails both, routed through the service worker. Same-origin is checked with window.origin, because an about:blank frame reports location.origin as "null". I caught that one with a real wallet-extension test.
Proof
e2e: same-origin iframe on a clean release file, about:blank iframe, window opened on a clean release file, and with a wallet installed as an extension: blocked via window, EIP-6963, about:blank, srcdoc
manifest.json · content.ts · background.ts · new fixture scripts/fixtures/fake-wallet
#4

A captured verdict could be replayed with the status flipped

Found while fixing
Was
The key covered the sequence number, not the status. A capture-phase listener runs before the extension's own listener, so it could catch the real “fail” and re-post it as “ok” with the same valid key.
Changed
Fixed by the private channel (#2): page code never sees a verdict.
Proof
e2e: “replaying a captured verdict with status flipped”
#5

A getter could show the gate one method and the wallet another

Found while fixing
Was
A method getter returned eth_chainId when the gate read it and eth_sendTransaction when the wallet read it.
Changed
The request's method and params are read once, and the wallet receives a fresh copy. A non-string method is rejected.
Proof
e2e: “a method getter that changes between gate and wallet”
#6

Batched legacy calls skipped the check

Found while fixing
Was
sendAsync([{ method: 'eth_sendTransaction' }]) wasn't inspected, because the first argument was an array.
Changed
Every provider method other than request (send, sendAsync, internal ones like _rpcRequest) inspects its first argument as a string, a payload or a batch. It copies payloads and refuses signing while the page isn't verified.
Proof
e2e: “a batched legacy sendAsync call”
#7

Page code could replace ethereum.request

Found while fixing
Was
Assigning a function to ethereum.request wrote it onto the raw provider. The wrapper then called it with the raw provider as this.
Changed
The wrapper refuses to store functions on the provider and refuses defineProperty. Plain values, such as flags some libraries set, still go through.
Proof
e2e: “replacing ethereum.request on the provider”
#8

The raw provider leaked through event listeners and on()

Found while fixing
Was
Providers built on EventEmitter call listeners with the provider itself as this, and on() returns it. Either way, page code ended up holding the unwrapped wallet.
Changed
Callbacks passed in by the page are wrapped so they receive the wrapper as this, with a stable identity so removeListener still works. Any method that returns the raw provider returns the wrapper instead. ethereum.providers entries are wrapped too.
Proof
e2e: “the raw provider leaking as `this` in an event listener”, “the raw provider returned by on()”
#9

Re-check must never turn a failed page green

Found while fixing
Was
This risk appeared when Re-check became an in-place re-verification (#21). If the server is restored while a tampered page is still open, a fresh check would pass even though the tampered code already ran in that page.
Changed
A failed verdict is sticky in both scripts. Only a reload clears it.
Proof
e2e: “re-check after restoring the server keeps a failed page blocked”

False alarms and wasted work

These would have shown a red banner, or kept re-hashing the whole bundle, on real dApps the demo doesn't resemble.

#10

*.eth.limo sites without a record went red

High
Was
Any *.eth.limo/*.eth.link site that never adopted WebSeal showed “Blocked”, a red banner, and refused signing.
Changed
The ENS lookup now reports when it succeeded but found no record. A name derived from the host with no record is treated as an unknown site (grey), and the popup explains why. A lookup that fails outright still fails closed, since the site may have a record.
Proof
e2e (live Sepolia RPC): “derived *.eth.limo name without a record is unknown, not failed”, “…: no banner”
extension/src/ens.ts · background.ts · popup.ts
#11

Single-page-app routes went red

High
Was
The current URL path was checked as a file. After pushState('/dashboard'), the next check found /dashboard missing from the manifest. Opening a deep link directly failed the same way.
Changed
New core function verifyDocument: the document is checked by the URL it was originally loaded from (saved when the page starts), and a route that isn't in the manifest passes when its HTML is byte-identical to a page in the release.
Proof
unit test “verifyDocument accepts client-side routes only when the HTML is a release page”; e2e “client-side route change (pushState) stays ✓”
core/src/index.ts · content.ts
#12

Every network request re-verified the whole page

High
Was
The performance observer fired for every resource, including fetch, so 10 page fetches caused 10 full re-fetch-and-re-hash runs. A dApp polling its RPC would never stop hashing.
Changed
Both observers now react only to new scripts and stylesheets. Verification is incremental: only files not already checked are fetched and hashed.
Proof
e2e: “ordinary fetches (RPC polling) do not trigger re-verification”
#13

Clean plain-HTTP sites went red

Found while fixing
Was
Web Crypto exists only in secure contexts, so on an http:// host other than localhost the hashing threw and the page failed.
Changed
Core falls back to a small pure-JS SHA-256 when crypto.subtle is missing. A unit test checks it against Web Crypto at every padding-boundary length and on 100 KB of input.
Proof
unit test “JS SHA-256 fallback matches Web Crypto…”; e2e “plain-http (insecure context) clean site verifies”

Reliability, CLI and release

#14

Popup forgot the verdict after about 30 seconds idle

Medium
Was
Per-tab results lived in the service worker's memory. After Chrome stopped the worker, the badge still showed ✓ but the popup said “No trust anchor for this site”.
Changed
Per-tab state is stored in chrome.storage.session, which content scripts can't read, and is cleared when the tab closes.
Proof
e2e: “popup keeps the verdict after the service worker restarts”
#15

The CLI ignored the webseal.<name> fallback

Medium
Was
The extension fell back to the subname but verify --name didn't, so the limited-rights CI key setup would fail in the CLI.
Changed
record and verify --name use the same name-then-subname lookup and print which name the record came from.
Proof
Run by hand: the error names both lookups. The case where a record exists only on the subname hasn't been seen live.
cli/src/ens.ts · cli/src/index.ts
#16

The release workflow anchored builds that weren't deployed

Medium
Was
Every push to main wrote the new hash to ENS, but the workflow only uploaded a CI artifact. Everyone who had pinned the name would see red, and every push cost gas.
Changed
New order: build, write the manifest (hash captured), deploy (placeholder), then verify the live site against the new hash, retrying for up to five minutes. Only after that does it publish. Anchoring needs the WEBSEAL_SITE_URL variable, runs are serialized, and publish skips the transaction when the record already has the value.
Proof
The YAML parses, and the hash extraction was tested against real CLI output. It hasn't run on GitHub yet.
.github/workflows/release.yml
#17

The banner could be removed, and its HTML wasn't escaped

Medium
Was
Page code could delete the banner. File paths went into its HTML unescaped.
Changed
Text is escaped, the banner's inline styles are marked !important, and it re-attaches itself when removed. The badge stays authoritative either way.
Proof
e2e: “banner comes back after page code removes it”
#18

“Pin current manifest hash” could pin an error page

Low
Was
When there was no report yet, it fetched over hard-coded http://, didn't check for a 404, and pinned whatever came back.
Changed
It uses the tab's own origin, requires an OK response, and checks that the body parses as a manifest before pinning.
Proof
Typechecked. This fallback path isn't covered by a test.
#19

“Pin ENS name” only accepted .eth

Low
Was
DNS names imported into ENS (such as example.com) were rejected.
Changed
Any dotted name is accepted. A name that doesn't resolve shows up as a lookup error.
Proof
Typechecked, not covered by a test.
#20

CLI publish didn't confirm what it wrote

Low
Was
It didn't read the record back, didn't check the transaction status, and would send a transaction to a name with no resolver. verify --expect accepted any string.
Changed
publish skips the transaction when nothing changed, errors on a failed transaction or a missing resolver, and reads the record back. --expect must be 64 hex characters.
Proof
Run by hand: the --expect check and publish --dry-run. A real publish needs a key and Sepolia ETH.
#21

Re-check just reloaded the page

Low
Was
The content script's recheck handler was unused, and the popup button reloaded the tab.
Changed
Re-check now re-verifies in place: fresh ENS lookup (skipping the cache), fresh manifest, every file again. It falls back to a reload when the tab has no verifier. Combined with #9, it can't clear a failure.
Proof
e2e: “re-check in place on a clean page stays verified, without a reload”

Setup: Node 22 and a Windows path bug

Installed Node 22.23.4 and pnpm 10.28.0 through nvm. The e2e scripts now use fileURLToPath.

Round 2: the open items, the demo recorder

Each round-1 “remaining issue” that could be done from this machine, plus what the new demo recorder exposed.

#23

A tampered same-origin frame could use a clean page's wallet before it was checked

Critical
Was
A frame's own scripts run before its verification finishes (load plus 150 ms). In that gap, a tampered frame inside a clean page could call parent.ethereum while the page was still green.
Changed
WebSeal's scripts in same-origin frames share one isolated world, so a frame now registers with its top page (or its opener) synchronously at document_start, before any of its own scripts run. The top page then holds signing until the frame reports. about:blank, srcdoc and blob: frames only contain code the page itself wrote, so they don't hold signing. A frame that never finishes loading stops holding after 5 s.
Proof
e2e: “a tampered same-origin frame using the page wallet at once” (blocked, page turns ✗), stable across 3 full runs and 8 repeats of the scenario
content.ts
#24

A frame could plant code in the page and delete itself before being checked

Found while fixing
Was
With #23 in place, a frame could set a timer in the top page and remove itself while still unverified. Removing an unverified frame would have dropped its hold, and the planted call would later run on a green page.
Changed
A frame or window that goes away while still unverified fails the page: “went away before it could be verified”.
Proof
e2e: “a frame that plants code in the page and removes itself” (the wallet never sees the transaction, page turns ✗)
#25

No answer from the background worker counted as “no anchor”

Found while fixing
Was
If the content script's message to the service worker failed, the missing answer was read as “this site has no anchor”, which means unknown and signing allowed. That fails open on an anchored site, and a frame that hit this would release its page's hold.
Changed
Only an explicit answer counts. The request is retried four times, and if the worker still doesn't answer the page fails with “could not reach its background worker”.
Proof
Code review and typecheck. There's no test that makes the worker unreachable.
#26

Wallet-specific globals reached the raw wallet

High
Was
window.phantom.ethereum, window.coinbaseWalletExtension and similar globals skipped the wrapper.
Changed
17 known wallet globals get the same accessor as window.ethereum. Inside a namespace object, any property that looks like an EIP-1193 provider comes back wrapped.
Proof
e2e with a wallet installed as an extension that exposes both globals: “tampered page blocked via phantom”, “… via coinbase”
main.ts · scripts/fixtures/fake-wallet
#27

Real wallets and libraries could break on the stricter wrapper

Medium
Was
The wrapper refused every defineProperty on the provider, and wrapping a frozen provider's methods would make every property access throw.
Changed
Plain data values may be defined (functions and accessors still may not). Frozen methods are returned as they are; they run with the wrapper as this, so their internal calls still go through the gate.
Proof
All suites pass. Real MetaMask still hasn't run against it (see below).
#28

Red between the deploy and the ENS transaction

Medium
Was
A single-hash record means visitors see red from the moment the CDN serves the new build until the ENS transaction confirms.
Changed
A record may list two hashes, v1:sha256:<new>,<old>. webseal publish --keep-current adds the new hash before the deploy, and the workflow pre-announces, deploys, checks the live site, then finalizes. The extension and verify accept either hash.
Proof
unit test for the record format; CLI e2e and browser e2e “rollout record with two hashes accepts the served build”. The workflow's YAML parses; it hasn't run on GitHub.
core · cli · extension · release.yml
#29

ENS code paths could only be tested with a key and a live chain

Medium
Was
Pinning by name, the subname fallback, and the record format were only exercised live, and there's no record on chain yet.
Changed
New fixture scripts/fixtures/fake-ens-rpc.mjs: a local JSON-RPC server that answers ENS Universal Resolver lookups from a map, so the real viem lookup code runs end to end offline.
Proof
CLI e2e: subname-only record, rollout record, stale record, no record. Browser e2e: pin by name ✓, popup shows the ENS anchor, stale record ✗.
#30

WebAssembly and service workers weren't checked

Medium
Was
.wasm fetched at runtime and service-worker scripts (which can rewrite every response) were never hashed.
Changed
Fetched .wasm files count as code. The scripts of the origin's service worker registrations are verified, and new registrations are picked up.
Proof
e2e: “unlisted WebAssembly fetched at runtime flips to ✗”, “unlisted service worker registered by the page flips to ✗”
#31

One RPC for ENS lookups

Low
Was
If publicnode was down, every lookup failed. Because a failed lookup fails closed, *.eth.limo sites went red.
Changed
Without a custom RPC, reads go through viem's fallback transport over public RPCs I checked from here (publicnode, then 1rpc.io for Sepolia, plus drpc for mainnet). A custom RPC is used on its own. CLI transactions go to one RPC only.
Proof
Live reads work. The switch to the second RPC wasn't forced in a test.

Remaining issues

Not fixed, or not verifiable from this machine, as of round 2. Ordered by what matters most for the demo and the security claim.

  • Needs you · before the demo Real MetaMask hasn't run against this build. I downloaded MetaMask's official Chrome build (its SHA-256 matched GitHub's), but the permission check blocked me from running a third-party wallet's code in automation. The manual test and the recorder's MetaMask mode are written but have not been run. Either docs/TESTING.md §1 by hand, or pnpm demo:record --setup --metamask <dir> --profile .demo-profile once, then MM_PASSWORD=… pnpm demo:record --metamask <dir> --profile .demo-profile (§5).
  • Design limit Wallet internals, unlisted wallet globals, non-EVM providers. A wallet whose methods return internal objects, or that exposes a global not on the list of 17, can still be reached unwrapped. Solana-style providers aren't gated. Any gate that lives in the page's world has this limit. Lasting fix: the wallet asks WebSeal for the verdict (a wallet integration or Snap).
  • Edge cases Frames. A same-origin frame nested under a cross-origin parent links to the top page only. A legit page that removes a same-origin URL iframe before it's verified now fails (deliberate, see #24). A frame that never finishes loading holds signing for up to 5 s. Watch for false alarms on real dApps that use same-origin iframes.
  • Needs a key and Sepolia ETH Live ENS publish, the subname CI key, and the workflow on GitHub. Every lookup path now runs against the fake ENS RPC, and live reads work. Writing, read-back, --keep-current on a real record, and the two-transaction workflow have not run on chain. docs/TESTING.md §2–4, then record with --ens-name.
  • Cost Two ENS transactions per release. The rollout record costs a pre-announce and a finalize transaction. That's cheap on Sepolia; on mainnet, weigh it against a short red window. Skip the pre-announce step if the window is acceptable.
  • Unchanged from README Known limitations of the approach. A server that serves different bytes to the re-fetch, web workers' own imports, WebAssembly fetched from a URL not ending in .wasm, trust in the RPC, and a poisoned source repo. Hash real response bodies via the debugger API, read ENS through a light client.
  • Housekeeping Video format, Playwright version, git. The video is WebM (VP8). YouTube takes it; convert to MP4 if a form insists. The test wallet in the automatic video has no confirmation window, and the caption says so. Playwright is pinned to 1.49.1 to match the Chromium on this machine. The project isn't under git. Run git init before pushing (TESTING §4). Upgrade Playwright together with npx playwright install chromium.
